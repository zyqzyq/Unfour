## 现场只需一次业务请求

1. 退出旧 Unfour，使用本轮单文件主程序打开原堡垒机目标，停在已登录的空闲 POSIX 命令行。运行一次“已登录终端 curl”能力检测，确认传输、工具和两次恢复均通过。
2. 按现场授权发送一次原 JSON POST。核对状态码和响应正文，打开响应区的“耗时”。记录总耗时、准备、输入、确认次数、等待确认、远端执行与回传、curl HTTP 总耗时、至首字节和恢复。仅回传这些数字与状态码即可。
3. 回到同一终端，执行一次获准的 `ls`，确认仍可交互。若请求结果未确认，保留固定错误码并先核对服务端结果，避免重复 POST。恢复不确定时遵循界面的隔离提示。

## 本机同条件对照

在修改生产代码前编译旧 Rust 驱动，修改后再用同一回环 SSH 测试端对比。两次使用各自生产构造器
生成的命令，使用相同合成 URL、鉴权头、查询和正文。SSH 对端在每条完整输入行到达时延迟处理，
返回固定 97 B 测试数据；驱动经过原生 SSH 写入、完整 ACK、输出解码、恢复与默认 30 秒总截止。
注入延迟只施加于指定的完整行，不涵盖系统调度等额外开销。该测试端不运行 HTTP。

## 请求、传输和耗时字段

- 每次从子 shell 验证解码器能输出已知字节并正常退出。通过后每个 D 行携带最多 180 个原始字节的 base64，只有编码器时使用原有 48 字节八进制。两种编码均限制为线上 242 字节（含行首与换行）。一次只发一行，校验操作标识、序号、编码长度及完整回显，再发送下一行。最终行继续核对总行数与总编码长度。
- 固定 bootstrap 长度由 1,721 B 降到 1,697 B。选择更紧凑的编码已能减少串行等待，没有启用多行窗口。原有长输入丢失和中继容量仍决定哪些优化适合现场。
- curl 7.29 的普通 JSON 从三次无网络 curl 预检减为一次。共用的严格 CLI 控制参数同时用于预检和业务传输，`--version` 放在检查参数最后。URL、凭据及正文经已验证的 shell 内建 printf 和管道传入 curl 配置，不写远端临时正文文件。首字节为 `@` 的正文单独验证 `--data-raw`，7.29 明确拒绝并保持零次业务 HTTP。
- 准备覆盖启动至 ACCEPT；输入覆盖数据发送至结束确认。远端执行与回传覆盖结束确认后等待、预检、HTTP、输出读取及解码。curl 的 `time_starttransfer` 和 `time_total` 从目标机本次 HTTP 传输开始累计；ACK 等待包含在输入时间内，首字节包含在 curl 总耗时内，各列不能直接相加。
- 阶段数字随本次完整响应返回，包括 HTTP 错误响应。历史仍记录原有总时长；操作未取得完整响应时，使用原有阶段错误码。
