## Call chain and correction

- Desktop `tabToInput` preserves Auth JSON for save and Send; Send prepares
  sendable Headers/Query and generated Content-Type separately. Tauri/API
  adapters dispatch through CommandBus.
- `send_api_request_in_environment` resolves Workspace, environment, and
  temporary variables through a single resolver snapshot. Auth JSON, URL,
  body, and Header/Query keys/values are resolved before `materialize_auth`.
  Scripted sends apply pre-request transformations, then use the same resolver
  and auth materializer.
- `send_cancellable_with_secrets` sends the resolved input and persists
  `sanitize_with_secrets` output. Runtime credential provenance and resolver
  secret values scrub request/response data and diagnostics; activity contains
  method/status metadata rather than credentials.
- OpenAPI loads collection-scoped saved requests and Workspace/method-scoped
  histories. Its internal matching copies now use the same auth materializer
  as Send before the existing history redaction projection. Basic encoding
  still uses reqwest request construction without network I/O.
- History copies use the saved auth context only for redaction, including
  legacy custom API-key slots and credential echoes. No auth row is injected
  into a history. Missing/different auth structure remains a non-match.
  The document continues to use sanitized saved definitions and sanitized
  response examples; matching copies never become serialized export fields.

Enabled explicit Headers override generated auth case-insensitively after
trimming header names. Explicit Query keys override by exact case-sensitive
equality; API-key configuration names are trimmed by the shared materializer.
Disabled rows do not suppress injection. Runtime custom API-key provenance now
uses the same trimmed configuration key and trimmed header-name comparison,
so whitespace around an explicit custom credential header cannot bypass
scrubbing. This also protects a different explicit Query credential value when
the configured API-key name has surrounding whitespace.

No dependencies, database Schema, Cloud Sync protocol/Secret support, V1/V2
backup formats, versions, tags, Release, or remote refs changed.

## Remaining limits and RC decision

Matching requires equality of the full redacted request snapshot (Workspace,
name, method, URL, Header/Query arrays, and public body content), with semantic
JSON equality and equivalent encoded/literal redaction markers. Markers are
never wildcards. The fix does not drop auth rows, compare only URL/method, or
try a pre-auth fallback to obtain a response.

Historical variable values, dynamic auth key names, script transformations,
and frontend-generated/filtered rows cannot always be reconstructed from a
saved definition. Different public snapshots remain unassociated and export
the default response. Secret references used as auth values can match through
redaction; arbitrary Secret references without the same auth/credential
provenance are not resolved at export time. Current environment values must
not be treated as historical execution values.

History has no saved-request ID or auth metadata. Two definitions/executions
with identical public projections but different credentials (or auth schemes
whose header values were wholly redacted) remain indistinguishable. A matched
example establishes redacted snapshot compatibility, not secret identity.
No lost credential, variable, or truncated preview data is reconstructed.
Legacy custom API-key export redaction uses available auth/row values; this
does not add auth metadata to the standalone legacy-history repair.

The scoped fix can directly enter v0.11.0 RC verification: all final local
automated regressions above pass. The initial unrestricted-thread Flow timeout
remains a recorded test-load risk; the passing full rerun did not weaken its
assertions or budget. The default-ignored real OS Keychain smoke was not rerun
because this change adds no Keychain access or lifecycle behavior.

This is source readiness, not a verified/released v0.11.0 artifact. Fresh Linux
CI, signed platform RC builds, and native artifact/manual journeys remain
required by the original RC record. No workflow was dispatched here.

### Minimal correction and compatibility

Only OpenAPI's internal history matching/export projection changes:

- Malformed Auth JSON, invalid root/type/location types, unsupported schemes,
  and materialization errors produce no history matches for that definition.
  Its sanitized request remains in the document with the existing `default`
  response; valid neighbors continue to export. There is no attempt to ignore
  Auth, remove credential rows, or match the pre-auth definition.
- Valid Auth still uses Send's shared materializer, including Bearer, Basic,
  API Key Header/Query, explicit enabled overrides, disabled entries, trimmed
  Header names, exact Query key equality, and variable-reference behavior.
  Full public snapshot equality and Workspace/method discriminators remain.
- A historical request containing a redaction marker has lost credential
  information. Matching/status/history ID remain, but **all response body and
  Header examples are omitted**, including derived body schemas, rather than
  selectively trusting fields such as `echo` or `X-Echo`. Markers in name, URL,
  Header/Query JSON, and body are checked, including equivalent JSON escapes.
- Basic histories also omit response examples: the encoded Authorization pair
  does not supply the separate historical password to the existing scrubber.
  Explicit Basic/Proxy-Authorization rows receive the same treatment. Invalid
  historical Header/Query JSON likewise cannot establish safe provenance.
- Plain histories retain examples. Legacy plaintext Bearer/custom API-key rows
  with available historical values still scrub those values from body/Headers,
  preserving ordinary fields. The saved custom API-key context identifies the
  slot; its current value is not assumed to be the old credential.

No Send, legacy repair, history UI, schema, Cloud Sync protocol, V1/V2 backup,
Secret storage, dependency, or version changes. Export is read-only and saved
definitions remain intact. The response-example omission applies to currently
written credential-redacted histories too: existing persisted data cannot
reliably distinguish them from older, partially sanitized histories.

New coverage mixes fifteen invalid Auth shapes with four valid auth types in
one Collection, with tempting pre-auth/explicit-override histories. It verifies
default-only responses for invalid definitions and association for valid ones.
The rotation matrix covers four auth types, plaintext/redacted request rows,
both existing redaction versions, repair before/after, body/Header echoes,
Unicode-escaped markers, unchanged definitions, and read-only exports.
Both matrices run through JSON and YAML serialization. Existing ordinary,
Workspace/public mismatch, explicit-override, disabled-row, and auth-reference
regressions remain required and are included in the Rust suites.

### Historical-data limits and RC decision

`api_history` has no saved-request ID, historical Auth JSON, or persisted secret
provenance. `redaction_version=1` is used by both legacy repair and current Send,
so it is not proof that every historical response echo was scrubbed.
Identical redacted public projections still cannot distinguish credentials;
matching is snapshot compatibility, not credential identity.

Legacy repair can scrub values still present in classified plaintext request
slots before overwriting them. It cannot recover values already replaced with
markers, identify custom API-key slots without Auth metadata, or derive all
separate Basic credentials using the existing scrubber. Such old SQLite rows
can still contain ordinary-field echoes; this fix protects their OpenAPI output,
**does not claim complete historical-data erasure**, and does not rewrite user
history as a side effect of exporting.

Unlabelled values with no remaining credential slot/marker/provenance cannot
reliably be classified as secret or public. Historical variables, custom slot
changes, scripts, and truncated data are not reconstructed or guessed from
today's environment/Auth. Changing such data may also prevent strict matching,
in which case the existing default response is exported. No new fingerprints,
credential archives, passwords, or persisted metadata were introduced.
